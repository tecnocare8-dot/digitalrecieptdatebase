# スタッフアカウント（1つの会社の帳簿を複数人で使う）設計書

作成日: 2026-10-02 / 対象: オンライン版（main・Vercel・Googleドライブ保存）

## 1. 目的

今は「1人＝1つの Google アカウント＝1つの帳簿」で、会社の帳簿を複数人で使うには会社の Google アカウントのパスワードを共有するしかない。
代表者だけが Google でログインして会社のドライブとつなぎ、ほかの人（スタッフ）は代表者が発行した ID とパスワードで別々にログインして、同じ会社の帳簿に領収書を登録できるようにする。

### 決定事項（利用者との合意）

| 項目 | 決定 |
|---|---|
| 使い方 | 会社アカウントを代表者が持ち、スタッフはパスワードを知らずに別ログイン |
| スタッフのログイン | 代表者が画面で ID とパスワードを作って手渡し（メール不要） |
| スタッフの権限 | 登録＋自分が登録した分だけ見る・直す。削除不可 |
| 料金 | スタッフ追加は Pro の機能。上限5人。追加料金なし |
| 方式 | 既存の利用者（代表者）にスタッフを紐づける（「会社」表は作らない） |

### やらないこと

- スタッフのメール招待・メールでのパスワード再設定
- 代表者を複数にする、1人が複数の会社を切り替える
- スタッフごとの権限の出し分け（経理担当に全件を見せる等）
- スタッフ1人ごとの追加料金

## 2. 全体の考え方

- 帳簿の持ち主は今まで通り「利用者（代表者）」。ドライブ連携・Pro 期限・支払い記録は代表者が持つ。
- スタッフでログインしても、サーバーの処理はすべて**代表者の利用者ID**で動く（`driveForUser(ownerId)`、帳簿ロック `ledger:${ownerId}`）。そのうえで、見える範囲・できる操作をスタッフ用に絞る。
- 既存の表は変更せず、表「スタッフ」を1つ追加するだけにする。Vercel の Preview は本番と同じ Neon を使うため、追加のみの変更に留めて今の本番を壊さない。

## 3. データ

### 3.1 表「Staff」（app スキーマ）

| 項目 | 内容 |
|---|---|
| id | cuid |
| ownerId | 代表者の User.id（代表者が消えたら一緒に消える） |
| loginId | ログインID。全体で重複不可。英小文字・数字・`-` `_`、3〜32文字 |
| displayName | 表示名（帳簿の「登録者」に入る）。1〜30文字 |
| passwordHash | `scrypt` で変換した値（塩付き）。平文は保存しない |
| sessionVersion | 整数。削除・パスワード再設定のたびに増やす |
| failedLoginCount | 連続ログイン失敗回数 |
| lockedUntil | ログイン停止の終了時刻（null=停止なし） |
| lastLoginAt | 最終ログイン日時 |
| createdAt | 作成日時 |

削除は行を消す（論理削除にしない）。過去の領収書の登録者名は帳簿側に残るので困らない。

### 3.2 帳簿CSV・画像の説明欄

- `領収書一覧.csv` の末尾に「登録者」「登録者ID」の2列を追加する。
- 代表者が登録した分: 登録者＝代表者の名前、登録者ID＝空。スタッフの分: 登録者＝表示名、登録者ID＝Staff.id。
- 画像の説明欄（JSON）の `receipt` にも `registeredBy`・`registeredById` を持たせ、CSV 作り直し時に復元できるようにする。
- 既存の行・列が無い CSV は空欄＝代表者の分として読む（見出し名で列を探す既存の作りのまま）。移し替え作業はしない。
- 絞り込み・権限判定は登録者IDで行う（表示名を変えてもずれない）。CSV を Excel で直接書き換えられた場合も登録者IDを正とする。

## 4. ログイン

- NextAuth に ID・パスワード方式（Credentials）を追加する。セッションは今と同じ JWT。
- ログイン画面: 「Googleでログイン（代表者）」の下に「スタッフの方」欄（ログインID・パスワード）。
- JWT に `userId`（＝代表者ID）、`staffId`、`staffSessionVersion` を入れる。代表者は `staffId` なし。
- **毎回の確認**: スタッフの要求ごとに Staff 行を読み、行が存在しない、または `sessionVersion` が JWT の値と違えば 401 を返して強制ログアウトする（Pro 状態はここでは見ない）。これで削除・再設定が即座に効く。
- **パスワード**: 8文字以上。代表者が作成・再設定し、画面に一度だけ表示する（再表示不可）。
- **総当たり対策**: 10回続けて失敗したら15分停止。成功で回数を0に戻す。代表者がパスワードを再設定すると停止も解除。存在しないIDでも同じ文言・同程度の時間で返し、IDの有無を推測させない。
- 照合は `crypto.timingSafeEqual` で比べる。追加の部品（bcrypt 等）は入れない。

## 5. 権限

サーバー側で、ログイン中の人を `{ ownerId, staffId | null, displayName }` として受け取る共通関数（`requireActor()`）を作り、全窓口がこれを使う。画面で隠すだけに頼らない。

| 窓口 | 代表者 | スタッフ |
|---|---|---|
| `POST /api/receipts`（登録） | ○ | ○（登録者＝自分） |
| `GET /api/receipts/list` | 全件 | 自分の分だけ |
| `GET/PATCH /api/receipts/[id]` | 全件 | 自分の分だけ。他人の分は 404 |
| `DELETE /api/receipts/[id]` | ○ | × 403 |
| `GET /api/receipts/[id]/image` | 全件 | 自分の分だけ。他人の分は 404 |
| `GET /api/receipts/export`（CSV） | ○ | × 403 |
| `/api/settings`・`/api/drive/folder`・`/api/checkout*` | ○ | × 403 |
| `/api/stores`・`/api/stores/match`・`/api/invoice-lookup` | ○ | ○（会社全体の学習を共有） |
| スタッフ管理 `/api/staff*`（新設） | ○ | × 403 |

- スタッフの修正では「登録者」「登録者ID」を書き換えさせない。
- 件数制限・Pro 判定は代表者の状態と会社全体の件数で行う（今の `addPermission` をそのまま使う）。
- スタッフ追加は Pro 有効中のみ、かつ5人まで。Pro が切れてもスタッフは消さず、ログイン・自分の分の閲覧・修正は可、新規登録は不可。

## 6. 画面

- **ログイン画面（AuthGate）**: スタッフ用の ID・パスワード欄を追加。
- **設定ページ（代表者のみ）**: 「スタッフ」欄。一覧（表示名・ログインID・最終ログイン日）、追加、パスワード再設定、削除。作成・再設定時はパスワードを一度だけ表示し「コピー」ボタンを付ける。Pro でないときは「Pro で使えます」と案内。
- **一覧画面（history）**: 代表者には「登録者」列と登録者での絞り込み。スタッフには自分の分だけ表示し、削除ボタン・CSV出力・設定への導線を出さない。
- 画面上部に、スタッフでログイン中は「〇〇（スタッフ）」と表示。

## 7. 困ったときの表示

| 状況 | スタッフへの表示 |
|---|---|
| 代表者のドライブ連携切れ・フォルダ削除 | 「代表者にドライブの再連携を依頼してください」 |
| Pro 切れ・無料の件数上限 | 今の文言＋「代表者に連絡してください」 |
| ログイン停止中 | 「しばらくしてからお試しください（代表者がパスワードを再設定すると解除されます）」 |
| 削除された・パスワード再設定された | ログイン画面へ戻す |

## 8. 本番への影響

- DB は表追加のみ（migration 1本）。Preview に push した時点で本番 Neon に入るが、既存の表・本番アプリには影響しない。
- 環境変数の追加なし（既存の `NEXTAUTH_SECRET` を使う）。
- 既存の代表者の使い方は変わらない。CSV に2列増えるだけ。

## 9. テスト

- 権限の単体テスト（擬似ドライブ使用）: スタッフが他人の分を「見る・直す・画像取得」できない、「削除・CSV出力・設定・スタッフ管理・購入」ができないことを全窓口で確認。登録者IDを修正で書き換えられないこと。
- パスワード変換・照合、10回失敗で停止・成功で解除、再設定で停止解除。
- 世代番号変更・削除で、ログイン中のスタッフが次の要求で 401 になること。
- スタッフ追加: Pro でないと不可、6人目は不可、ログインIDの重複不可。
- 旧CSV（登録者列なし）を読めて代表者の分として扱うこと。
- 擬似ドライブで代表者とスタッフが同時に登録しても帳簿が欠けないこと。
- 既存の `npm run test:stores`・ビルドが通ること。
- 最後に Preview で、代表者とスタッフを2つのブラウザで実際に操作して確認する。
